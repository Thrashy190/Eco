# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

The maintainer writes in Spanish: **reply to them in Spanish**, with complete code examples when explaining technical things. Everything in the repository (code, comments, docs, UI text, commit messages) is **English**: the project is meant to be open source.

The app is called **Eco**: write that in docs and on screen. `eco` stays for the command, the repository, the Go module, the Docker image and service, paths, hostnames and identifiers in code.

## What this is

**Eco** is a self-hosted music app: a web app (installable on phones) that plays a [Navidrome](https://www.navidrome.org) library, searches both that library and a music catalogue (MusicBrainz), and downloads songs that are not in the library yet (yt-dlp + ffmpeg, tagged with the catalogue's metadata). Go backend, React + TypeScript web app (Vite) embedded in the binary. See `README.md` for users and `docs/architecture.md` for how it works.

Status: running on the maintainer's laptop with `docker compose up -d` (Navidrome + Eco + Cloudflare tunnel). Public hostnames: `music.<domain>` → Navidrome (Subsonic apps), `eco.<domain>` → Eco. A home server is the target. Go module path: `github.com/Thrashy190/eco`. License: MIT.

## Commands

```bash
make check          # gofmt, go vet, go test, tsc, vitest, vite build — what CI runs. Run it before finishing.
make run            # build everything + serve on http://127.0.0.1:8000 (needs Navidrome and a .env)
make web            # build only the web app into web/dist
make web-dev        # web app with hot reload on :5173, using the eco running on :8000
make doctor         # eco doctor: yt-dlp, ffmpeg, JS runtime, Navidrome, Spotify, cookies
make tools          # download yt-dlp into bin/

docker compose up -d --build                      # core: Navidrome + eco (`eco version` then says dev)
make docker && docker compose up -d --no-deps eco # deploy eco alone, with the release recorded in the image
docker compose --profile tunnel up -d             # + Cloudflare tunnel
docker compose --profile downloads up -d          # + Lidarr / Prowlarr / qBittorrent

./bin/eco get -n URL                  # dry run of the single-link download
./bin/eco likes <export|search|download|favorites|playlist|all> [--playlist NAME] [--first N] [--limit N] [--csv PATH] [--music DIR]
```

Tests are Go unit tests (`internal/match`, `internal/catalog`, `internal/catalog/musicbrainz`, `internal/catalog/itunes`, `internal/imports`, `internal/lists`, `internal/library`, `internal/media`, `internal/server`, `internal/connect`, `internal/spotify`, `internal/userdata`, `internal/ytdlp`, `internal/tag`) plus `tsc` and vitest on the web app (`web/src/**/*.test.ts`, pure logic only). There is no automated browser test in the repository; when changing the UI, load it in a real browser (Brave/Chromium can be driven headless with puppeteer-core) and look at screenshots. Run that server with a scratch `DATA_DIR` and a fake `YTDLP_BIN`, and block `/rest/star`, `/rest/unstar`, `/rest/scrobble` and `/rest/createPlaylist`, because it talks to the real Navidrome. Importing and cleaning up write to Navidrome: test them on a throwaway one. Check a layout at phone, tablet and computer widths. `ECO_LIVE_MUSICBRAINZ=1 go test ./internal/catalog/musicbrainz -run TestLive -v` measures the real catalogue, at its one request per second.

## Rules that are easy to break

- **The web app is embedded** (`web/embed.go`, `//go:embed all:dist`). Editing `web/src/**` changes nothing until you rebuild (`make build` does both) *and restart the server*. A stale server once hid a fixed bug for several test runs. `web/dist/` is git-ignored except `.gitkeep`, which `go:embed` needs so Go builds and tests work before the first web build; the Vite plugin in `web/vite.config.ts` puts it back after each build. `gofmt` must never walk `web/node_modules`: the Makefile names `web/embed.go`.
- **Never aim a test at the real library or CSVs.** Use `--csv` and `--music` with a scratch copy. `--limit 0` means *no limit*, not zero: a "harmless" check with it started a real download. Back up `data/likes.csv` before running anything that rewrites it (the first read migrates the old Spanish CSV format in place).
- **`internal/match` decides which video is the song.** A wrong song in someone's library is worse than a failed download. Keep the duration, unwanted-version and title checks; add a test naming the real case for every change there. `Norm` keeps any alphabet (`\p{L}\p{N}`): collapsing non-Latin titles to "" made every Cyrillic/Japanese title of one artist look identical.
- **`library.Safe` strips leading dots.** A folder named `.5- The Gray Chapter` is hidden on Linux and Navidrome ignores it.
- **Search with YouTube first, YouTube Music only if unsure.** YouTube Music is slower and triggers 403s sooner; `--playlist-end 5` is mandatory there or yt-dlp pages through ~20 result pages per song.
- **When YouTube answers "not a bot", stop** (`ytdlp.IsBlocked`): retrying makes it worse. Cookies (`YT_COOKIES_BROWSER` on a desktop, `YT_COOKIES_FILE` on a server) are the fix; a fixed pause between downloads did not prevent it.
- **Liked songs are Navidrome favourites, not a playlist** (`eco likes favorites`, `internal/lists/favorites.go`). Navidrome stores each favourite's timestamp with nanosecond precision and lists the newest first, so songs are starred from the *oldest* like to the newest (a 3 ms gap between calls) and the favourites then read exactly like the Spotify likes. Run the sync only after the downloads finish: starring songs later puts them in front of newer ones. Only Spotify *playlists* (`--playlist NAME`) become `.m3u` playlists. The app *shows* favourites as a playlist (`/playlist/favorites`, the reserved ID `favorites`, always first in the library) but they stay stars in Navidrome: never turn them into a real playlist.
- **Navidrome's `path` field is synthetic** (`01-09 - Title.m4a`, not the real file name). Match songs by title + artist, tie-break by album then length (`findSong`), never by path.
- **yt-dlp rewrites the cookies file it is given.** `ytdlp.cookieCopy` hands it a private temp copy on every call; the original may be a read-only mount (`./secrets:/secrets:ro`) and without the copy every download exits 1 *after* downloading.
- **Downloads run in a scratch folder next to the destination** (`.eco-*`, hidden) so the final move is an atomic rename.
- **Imported media (podcasts, audiobooks, other) is audio only and lives in `data/media/`, never in `music/`** — Navidrome would shuffle audiobooks into the music. Pasting a YouTube link never keeps the picture: the maintainer decided against video. Eco serves it itself (`internal/media`, `ServeContent` for `Range`). Accept **only YouTube hosts** (`youtubeURL`, tested): arbitrary URLs would make the server fetch internal addresses. Items are keyed by the video id, which also validates the path segment; keep `ValidID`/`ValidKind` in front of every path join.
- **Recents, pins and playlist covers live in `data/users/<hash of username>/`** (`internal/userdata`), on the server so every device agrees, and per user. There is still no database. Navidrome has no way to store a playlist picture, so custom covers are only visible in Eco. Covers must stay real JPEGs (the browser converts them, `lib/image.ts`; the server checks with `jpeg.DecodeConfig`) and `coverTarget` checks the user can see the playlist, or a signed-in user could fill the disk.
- **An album looks the same however it is reached** (`AlbumPage` in `views/CatalogAlbum.tsx`). `/catalog-album/{id}` starts from the catalogue; `/album/{id}` shows the library at once and becomes the same page when `/api/albums/match` finds the album, keeping songs the catalogue does not list under "Also in your library". With no match it stays what the library holds, so it must never depend on the catalogue to play. `snapshot.find` prefers the copy on the same album, so a compilation does not answer for the studio album. Search results do not know their track number: downloads always re-read the full track (`runJob`).
- **Go 1.22 `ServeMux` panics at startup** when a method-less pattern overlaps a method pattern (`/api/media/preview` vs `DELETE /api/media/{id}`). Always give routes a method when mixing; run the server once after touching routes.
- **`{count && <x/>}` prints `0`.** Compare explicitly (`count > 0 && …`). Browser checks should look at every screen for stray `null`/`undefined`/`NaN`/`0`.
- **Commits are the release notes** (Conventional Commits): `fix:` gives a patch release, `feat:` a minor one, `docs:`/`ci:`/`test:`/`refactor:`/`chore:` none. The maintainer wants a semantic release for every feature or fix: CI does it on `main` with semantic-release (`.releaserc.json`), never tag by hand. Keep one change per commit so the notes read well.
- **An album with no answer is not an album that does not exist.** `/api/albums/match` answers 503 when the catalogue could not say in time and `album: null` only when it has none; the web app asks again on 503. Treating both as null left the page showing only the library's songs until it was opened a second time.
- **Offline downloads never give up on one bad moment** (`stores/saving.ts`). What is left is remembered (`CollectionRecord.songs`, `eco.saving.songs`) and picked up on launch, on returning to the app and on reconnecting. Time in the background or offline does not count as a failed try. A song that keeps failing is set aside and the rest carry on; three in a row means the server, so it waits. Navidrome reports a missing song as **HTTP 200 with a JSON error**, so check `streamProblem` before saving a response as audio: only code 70 means the song is gone. iPhones freeze web apps in the background and do not offer Background Fetch, so a download there only runs on screen (the screen is kept on with a wake lock) or while music plays; true background needs a native app.
- **A saved song plays from the device**, with no request for its audio (`load` in `stores/player.ts`); if that copy will not play and there is a connection, the retry streams it. Screens still show covers from the server while online: reading a blob per row of a long list is slower than the browser's cache.
- **Offline = IndexedDB blobs.** A song is deleted from the device only when no collection and no individual save holds it (`refs`/`direct` in `stores/offline.ts`). Screens that show a collection must fall back to `offline.collectionSongs` when `useOnline()` is false. The database name and version (`eco-offline`, 2) and the `localStorage` keys (`eco.session`, `eco.settings.*`, `eco.pos.*`) hold people's downloads and sign-in: renaming one loses them. Never read a route out of a saved collection (old records point at the removed favorites tab); use `collectionRoute`.
- **A 200 with an unreadable body arrives as `{}`** (`request` in `lib/api.ts`). Check the shape of anything saved on the device before saving and before using it (`isLibraryState`): a reload in the middle of an answer once saved `{}` as the copy of the library, and the app stayed blank on every launch, since it crashed before asking the server again.
- **A finished job is history, not state.** The server keeps jobs for an hour; a UI that resumes a job must check it is still running (`liveJob`), or it shows "added" for an item that was deleted. Do not compare `finished_at` with the time a card opened: it has one-second precision and a quick job looks old.
- **Artist names can hold several artists** (`Bad Bunny, Chuwi`), and Navidrome lists that as one artist. `ArtistLinks`/`splitArtists` give each one a link, leaving `Tyler, The Creator` whole. `/artist/name/{name}` finds the library's artist or shows what Spotify has by them.
- **The player lives outside React**, around the `<audio>` in `index.html` (`stores/player.ts`), so screens can come and go without stopping the music. Keep it that way, and use `useTime` for anything showing position.
- **iOS ignores `audio.volume`**, so the slider is hidden there (`canSetVolume`). Detect the system by name: a real iPhone reported `can_volume=1` from a read-back test. Any feature that sets the volume on another device cannot work when that device is an iPhone.
- **Hash routes, on purpose**: the server has no SPA fallback and the installed app always starts at `/`. Old addresses (`#/library/favorites`, `#/spotify-album/{id}`) must keep redirecting; people have them on their home screens. Recents saved as `spotify_album` hold IDs that mean nothing to MusicBrainz, so `entryRoute` finds them again by name (`/album-lookup`).
- **Cloudflare overrides `Cache-Control` on static file types.** Eco sends `no-cache`, yet `.svg`, `.png` and `.js` reach browsers with `max-age=14400` (its default Browser Cache TTL), so a reload does not fetch them again. Never rely on `no-cache` for a file a user must see change: each build also writes the icons as `icon.<hash>.ext` and links to those (`versionedIcons` in `web/vite.config.ts`), and anything else goes in `web/src` to get a hashed name. Keep `apple-touch-icon` an opaque PNG with a plain URL and `/apple-touch-icon.png` at the root: Safari fetches these by itself for bookmarks, and its bookmark icon went blank after a change that added `?v=` and an alpha channel. Installed iPhone apps keep their home-screen icon until reinstalled.
- **The service worker's file list is generated** (placeholders in `web/public/sw.js`, filled in by `web/vite.config.ts`) because asset names carry a hash. It must never touch `/rest` or `/api`.
- **Navidrome mounts the music read-only.** Only Eco writes: downloads only under `music/YouTube/`, deletion by an admin anywhere in `music/`. Lidarr's folder (`music/Lidarr/`) stays separate from `Originals/` because Lidarr matches against MusicBrainz.
- **Deleting a song is permanent, so it must be certain** (`library.FindSongFile`). Navidrome's `path` is synthetic: find the file by exact size + extension, confirm the title in its tags, and refuse unless exactly one file matches. Keep every check, and add a test naming the case for any change. Folders left with no music go too, including their `cover.jpg` (nearly every album has one), but any other file stops that. Never test deletion against the real Navidrome or `data/music`: start a throwaway Navidrome container on a scratch folder.
- **Accounts do not see each other.** Personal data stays per user: `internal/userdata`, `jobs.List(user)`, `internal/connect` (keyed by lowercase username; a foreign device ID answers exactly like a missing one). Anything new that lists activity must filter by `cred.User` and needs a test with two users. The shared library (songs, imported audio) is deliberately common to everyone.
- **Destructive actions are admin-only and checked on every request** (`adminOnly`, which asks Navidrome's `getUser`), never from the cached sign-in or what the app shows. `isAdmin()` in the app only decides what to offer.
- **Screens never talk to another device.** They call `stores/player.ts`; while `connect`'s `target` is set, the player forwards each control (`remote(...)`, undone by `applying` for commands arriving here). A new player control needs its `remote()` guard, a case in `applyCommand`, and its name in `connect.actions` on the server.
- **Tapping a song must make sound.** A song goes to another device only if the user chose that device (`chosen`); merely watching one that started playing, a tap plays here. Sending songs away by default made the app look broken whenever the other device was a forgotten tab, a phone asleep, or a browser refusing to start without a tap. Only a device *starting* to play stops the others (`wasPlaying`): reacting to "still playing" reports made devices pause each other. A device that does not answer within 6 s is dropped (`expectAnswer`). When testing, close every browser: one left running reconnects to the next run as a phantom device.
- **Song information comes from a `catalog.Source`, MusicBrainz by default** (`internal/catalog/musicbrainz`), because Spotify needed a Premium owner and could stop answering for hours (`Retry-After: 12157` was real). `CATALOG=spotify` still works. **iTunes is the backup** (`catalog.Fallback`, `CATALOG_BACKUP`), by the maintainer's decision knowing Apple means that data for promoting its store: it answers when MusicBrainz is down or lacks something. Every search asks both at once, because MusicBrainz never says "not found", it answers something else ("espresso" gives a band called Espresso, "metallica one" a live take): what both have comes first (`mergeTracks`), and the rest alternates, since iTunes alone buries Bad Bunny under covers. About 20 requests per minute (`perMinute`); past that, MusicBrainz alone. Apple joins artists as "A, B & C" with no way to tell them from "Earth, Wind & Fire", so iTunes songs keep it as one string. A song in both catalogues stays MusicBrainz's unless the lengths disagree. Deezer's terms forbid use associated with unauthorised downloads: do not add it without the maintainer deciding. MusicBrainz allows **one request per second per address**: `Client.wait` spaces them, answers are cached, and a search costs 2-3 requests, so never call it per row of a list (`FindTrack` runs when a song is actually downloaded). It has no popularity figures and lists every recording of a song: `rank.go` decides what comes first, and a real case that ranked badly belongs in a test there. A track ID is `recording.release`, because the release decides the album, number and cover in the tags. Nothing may wait on the catalogue to show the library: `/api/search` is library only, `/api/search/external` adds the catalogue after the typing stops, and everything asking it has `catalogTimeout`. While testing, do not hit the real API in a loop.
- **Artists in tags are separated by `; `** (`tag.Separator`), which Navidrome splits, never by a comma, which can be part of a name. On screen `readableArtists` turns it back into a comma. Rewriting the artist tag keeps a song's ID, favourite and playlists (tested on a real Navidrome); rewriting the album artist gives the album a new ID. `tag.SetArtists` keeps a copy and proves the audio identical before replacing a file. It only runs when an administrator asks, in Library clean-up.
- **An imported list is a real Navidrome playlist** (`internal/server/imports.go`), per user (`userdata.Import`; another user's answers like a missing one). Songs are only downloaded when asked. It cannot follow a Spotify playlist by itself: Spotify's API only lists a playlist's songs to its owner.
- **When YouTube says "not a bot", the queue stops for 30 minutes** (`youtubePause` in `runJob`), or a whole imported list would keep asking.
- **Above 760 px the page is a panel that scrolls by itself** (`#view`), not the window. Anything watching scroll uses `scrollRoot`. The widths in `lib/media.ts` and `styles.css` must agree. On a phone nothing changed: check both. Never navigate on focus: a closing window or dialog gives an input its focus back, and that once threw people onto the search page.
- **The next song is fetched ahead into memory** (`prepareNext`, a blob URL), which took changing songs from about 2.7 s to under 0.1 s and also works on iPhones, which ignore preload. Never read a big cover on each song change while the player is closed.
- **Auth is Navidrome's.** `/api/*` verifies Subsonic credentials with `ping`. The web app stores user + token + salt, never the password. Do not add an account system.
- **Secrets only in `.env` / `secrets/`**, never in compose files or code. `.env`, `secrets/`, `data/` are git-ignored.
- **React escapes text; keep it that way.** Never use `dangerouslySetInnerHTML`. Server data goes through `react-query`, shared client state through a `zustand` store in `web/src/stores`. Do not add a UI kit or a CSS framework: `styles.css` holds the design tokens the themes depend on.
- Spotify (development mode, only for `eco likes export` and `CATALOG=spotify`) returns at most 10 results per page (`limit=11` is a 400), needs the app owner to have Premium, and may omit fields (ISRC, genres): read them as optional.
- ffmpeg does not write the ISRC into M4A; Navidrome does not need it.
- **Dependabot's `fix:` is on purpose** (`.github/dependabot.yml`): merging an update to what ships in the app makes a release, so people get it. CI tools and development libraries use `ci:` and `chore:`, which make none.
- **`main` cannot be force-pushed or deleted** (the "Protect main" ruleset). Direct pushes and release tags still work.

## Layout

`cmd/eco` (CLI) · `internal/{server,engine,catalog,match,ytdlp,tag,spotify,subsonic,imports,lists,library,jobs,media,userdata,connect,config}` · `web/src/{lib,stores,components,views}` (UI), `web/public` (icons, manifest, service worker, `boot.js`) · `scripts/` (Lidarr hook, `upload.sh`) · `docs/` · `.github/` (CI, Dependabot, issue and pull request templates) · `Dockerfile`, `docker-compose.yml` (+ `docker-compose.vpn.yml`).

Before the Go rewrite the tool was Python (`bajar.py`, `likes.py`) with Spanish docs; a backup of those sources is in `data/backup/` on the maintainer's machine, not in the repository.
